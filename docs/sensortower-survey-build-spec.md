# SensorTower 機能利用状況調査 — フォーム構築仕様書

Ninout MCP でフォームを構築するための実装仕様。この文書だけで構築が完結するように書いてある。

- **フォーム名**: `SensorTower 機能利用状況調査`
- **カラーラベル**: `glacier`
- **規模**: 109ステップ / 分岐ロジック59本 / 表示ロジック58件（表示ロジックは後追い・管理画面作業）
- **公開**: **しない**。未公開（編集中）のまま完成させ、プレビューURLを返すこと。

## 1. 構築手順

1. `create_survey` でフォームを作成（開始ステップ・最終ステップが自動生成される）
2. `create_question` で S2〜S108 を作成（`order_index` は「S番号 − 1」）
3. `add_answer_item` / `update_question` で各ステップの選択肢・入力欄・オプションを設定
4. `order_questions` で最終順序を確定（最終ステップが末尾に来ていることを確認）
5. `list_questions` で全 question_id と answer_item_id を取得
6. `import_logics` で分岐59本を一括投入
7. `create_questionnaire_variable` で置換テキストを1件作成
8. プレビューで分岐検証（§7のチェックリスト）
9. 表示ロジック58件は**管理画面での手作業**（§6）。MCP非対応

### 繰り返し構築の考え方

S6〜S96 の91ステップは、**29機能ぶんの同一テンプレート（§4）の反復**。機能マスタ（§3）の `機能名` と `説明文` を差し込むだけで生成できる。手で1つずつ書き下ろさず、機能マスタをループして組み立てること。

## 4. 機能ブロック共通テンプレート（29機能ぶん反復）

`[機能名]` `[説明文]` を機能マスタから差し込む。

### A: 認知ステップ

- **質問タイプ**: テキスト選択（`answer_type: "2"`）
- **質問文** (`rendered_sentence`):
  ```
  【[機能名]】
  [説明文]

  この機能を知っていますか？
  ```
- **選択肢** (`answer_items`, 順序固定):
  1. `知っている`
  2. `知らない`
- **オプション**:
  ```
  is_single_select: true
  is_check_and_go:  true
  is_range:         true
  range_min:        1
  is_shuffle:       false
  ```

### B: 利用度ステップ

- **質問タイプ**: テキスト選択（`answer_type: "2"`）
- **質問文**: `【[機能名]】をどの程度利用していますか？`
- **選択肢**:
  1. `よく使っている`
  2. `時々使っている`
  3. `使ったことがある程度`
  4. `使っていない`
- **オプション**: A と同じ

### C: 重要度ステップ

- **質問タイプ**: テキスト選択（`answer_type: "2"`）
- **質問文**: `【[機能名]】は、あなたの業務においてどの程度重要ですか？`
- **選択肢**:
  1. `非常に重要`
  2. `重要`
  3. `普通`
  4. `あまり重要でない`
  5. `全く重要でない`
- **オプション**: A と同じ
- **分岐なし**（順番通り次のステップへ進む）

> **必須設定の注意**: テキスト選択では `is_required` は効かない。必ず `is_range: true` + `range_min: 1` で必須にすること。
>
> **選択肢数の注意**: テキスト選択はデフォルトで選択肢が2つ生成される。3つ以上必要なステップは `add_answer_item` で追加してから `update_question` の `answer_items` で一括更新する。

## 7. 分岐ロジック（59本）

`import_logics` で一括投入する。question_id / answer_item_id は `list_questions` で取得した実IDに解決すること。

### 7.1 機能ブロックの分岐（58本）

各機能について2本ずつ。**この2本セットがないと「知らない」人が利用度・重要度のページを通過してしまう**（分岐は「条件一致でジャンプ」であり「不一致でブロック」ではないため）。

```

  order_index:  0,
  logic_items: [

      answer_item_id: <「知らない」のID>,

  ],
  logic_action: { question_id: <機能マスタの「分岐先」ステップのID> }

# 利用度ステップの分岐

  question_id:  <利用度ステップ(B)のID>,

    { question_id: <利用度ステップ(B)のID>,
```

分岐先の一覧は §3 の機能マスタ「分岐先」列を参照。**カテゴリ最後の機能の分岐先は、次のカテゴリ見出しステップ**（例: #14 → S48、#30 → S102）。

## 8. 表示ロジック（58件 / 後追い・管理画面での手作業）

**今回の構築では設定しない。** 以下は後日追加する際の手順。MCP非対応のため管理画面から設定する。

- **対象**: S103（Q3-2）の29個の機能選択肢（`特にない` は対象外・常時表示）
- **設定**: 各選択肢に「非表示条件」を **AND** で2件

| 選択肢 | 非表示条件1 | 非表示条件2 |
|---|---|---|
| `[機能名]` | 当該機能の重要度ステップ（C）で `非常に重要` を**含まない** | 当該機能の重要度ステップ（C）で `重要` を**含まない** |

この書き方により、重要度ステップに到達しなかった人（知らない／使っていない）も未回答扱いで自動的に非表示になる。

> **設定タイミングの注意**: 公開後は選択肢の削除ができなくなる。表示ロジックを入れるなら**公開前**に設定すること。

## 10. 設計上の決定事項（変更しないこと）

構築時に「こうした方が良いのでは」と迷ったら、以下は検討済みの結論なのでそのまま従うこと。

| 項目 | 決定 | 理由 |
|---|---|---|
| マトリクスへの集約 | **しない**。1機能ずつ逐次で聞く | 依頼元の明示的な選択。「選択で回答終了」により1クリック遷移になるため所要時間は15〜25分に収まる |
| 回答者の識別設問 | **入れない** | 依頼元の判断。全体傾向のみの集計となる前提 |
| 導入文の目的表記 | SimilarWeb 移行検討を**明記する** | 依頼元の判断。過大申告バイアスは「個人の評価には使わない」旨の一文で緩和 |
| 「契約対象外」の選択肢 | **入れない** | 30項目すべてが現契約またはトライアルの範囲内であることを確認済み。契約外の要望は S108 の捕捉質問で拾う |
| 「該当5つ以下ならQ3-2をスキップ」 | **実装しない** | 選択件数を数えて分岐する仕組みがない。質問文に「5つ以下の場合はすべて選択」と明記して代替 |
| Q4 の機能別独立設問化 | **しない**。5つの汎用入力欄にする | 選択した機能名を入力欄ラベルに動的展開する仕組みがない。質問文に置換テキストで機能名を表示して代替 |
| Q4 の必須化 | **しない**（任意） | 離脱率を優先 |
| SenseAI の扱い | 実績ベースの29項目とは**別セクション・別ページ** | トライアル中の機能であり、同一のランキング表・重要度比較に混在させないため |
